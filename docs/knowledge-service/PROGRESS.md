## Уточнённый план Этапов 1–7

Общий принцип: всё, что не требует ответов, делается на фейках и чистых функциях. Реальные адаптеры к внешним системам — только по подтверждённым контрактам. В столбце «зависит от» — вопросы, без ответа на которые этап **закрывается по критериям ТЗ**, но **не работает в контуре**.

### Этап 1. Каркас

**Предусловие:** SDK в сессии (Q1). Первым делом — `dotnet build` существующего решения как точка отсчёта, чтобы отделить чужие предупреждения от наших.

1. Проекты по D1, добавление в `AIKnowledge.sln` и папки решения; пакеты — в `Directory.Packages.props` (Q17); `out/` — в `.gitignore`.
2. `KnowledgeServiceOptions` (все секции ТЗ 10 по D3/D4); плейсхолдеры в `Web/appsettings.json` и `appsettings.json` CLI.
3. Порты в Core:
   - `IEmbeddingClient`, `IStructuredLlm` (+ `PromptTemplate`, `LlmResult<T>`), `IReranker`;
   - `IWikiSource`, `IOrgSource`, `ISearchStore`, `IIngestStateStore`, `ILlmCache`;
   - `ITokenEstimator` (`символы / CharsPerToken`);
   - `IIdentifierParser` + заглушка (Фаза 2).
4. Фейки в Tests: хэширующий эмбеддер (детерминированный, нормализованный вектор нужной размерности), скриптуемый LLM, in-memory хранилища и источники.
5. Адаптеры:
   - OpenSearch: управление индексами — `{Prefix}{name}-v{N}`, создание версии, переключение алиаса;
   - маппинги пяти индексов `ks-*`, включая `doc_code` в `ks-chunks` (Фаза 2) и `access`;
   - анализаторы: `russian` + подполе `.exact` + `char_filter` `ё→е`;
   - LLM поверх `IChatClient`: JSON schema, валидация, один повтор;
   - реранкер (TEI `/rerank`);
   - FRIDA — заглушка (D8).
6. Минимальная правка `Assistant`: привязка `AssistantOptions` (Q16).
7. CLI: Generic Host + общий `AddKnowledgeService()`. Команды:
   - `check`: OpenSearch — пинг, версия, плагин `knn`; FRIDA — размерность; Gemma — JSON по схеме; реранкер. Вывод `OK / FAIL / SKIP + причина`;
   - `index create|switch|list` для версий и алиасов (ТЗ 5.1).
8. `/health` в `Web` — те же проверки, что у `check`.
9. Интеграционный тест `_analyze` для `.exact`: проверить, не ломает ли `asciifolding` кириллицу и `ё` (ТЗ 5.1). Запускается только в контуре.

**Готово, когда** (ТЗ): решение собирается, unit-тесты на фейках зелёные, `check` реализован, маппинги покрыты JSON-тестами.
**Зависит от:** Q1 (сборка в сессии), Q16, Q17; для работы в контуре — Q3, Q4, Q8, Q10.

### Этап 2. Реестр сущностей

1. Чистые функции: генерация алиасов (ТЗ 6.1.3) и нормализация `aliases_norm` (6.1.4):

   - подразделения — без типовых слов;
   - сотрудники — пять форм ФИО.
2. Адаптер `IOrgSource` из индекса оргструктуры (D9).
3. `ingest orgs`: bulk-запись в `ks-entities`, удаление исчезнувших сущностей.
4. `inspect entity <name|id>`; `GET /api/entities/{id}`.
   Уточнение плана: в ТЗ эндпоинт за этапом не закреплён. Ставлю его сюда, потому что он использует ту же карточку, что и `inspect entity`.

**Готово, когда** (ТЗ): тесты алиасов и нормализации (включая сотрудников и ОПФ) зелёные.
**Зависит от:** для контура — Q7 (поля оргструктуры). Критерии закрываются без ответа.

### Этап 3. Базовая индексация вики (без LLM)

1. Адаптер `IWikiSource` из индекса вики (D9); `content_hash` нормализованного HTML; `pipeline_version`.
2. `ingest wiki --full | --incremental | --limit N | --ids a,b,c`; пропуск неизменённых; удаления с каскадом (юниты, факты, `linked_doc_ids`, `attributes`); переиндексация документа = удалить и записать заново.
3. Парсер HTML → `ParsedDocument` (AngleSharp, Q17), каждое правило ТЗ 6.2.2 — отдельный тест.
4. Чанкинг: все секции `unknown` → по абзацам; таблицы режутся по строкам с повтором шапки; бюджет токенов и счётчики превышений.
5. Эмбеддинги с префиксами (D8), батчи и параллелизм из конфига.
6. Запись в `ks-chunks` и `ks-ingest-state`; ошибка документа → `failed` и идём дальше; итоговая сводка.
7. `ingest wiki --dry-run --sample N` → `out/ingest-dryrun-<ts>/` (JSONL + базовый `review.md`).
8. `POST /api/ingest/{source}` (фоном) и `GET /api/ingest/status/{taskId}`. Уточнение плана: в ТЗ эти эндпоинты за этапом не закреплены.
9. `inspect doc <doc_id>`.

**Готово, когда** (ТЗ): тесты парсера, чанкинга и бюджета зелёные; повторный прогон без изменений ничего не переиндексирует (тест на фейках).
**Зависит от:** для контура — Q4, Q5 (FRIDA), Q6 (индекс вики: особенно есть ли полный HTML).

**Готово, когда** (ТЗ): тесты RRF, сборки контекста и метрик на синтетике зелёные; `RUNBOOK.md` доведён до первого eval.

### Этап 5. LLM-обогащение

1. Промпты — встроенные ресурсы `Prompts/{id}.md` с шапкой (`id`, `version`, переменные); JSON schema генерируется из C#-типов; версии промптов входят в ключ кэша и в `extractor_version`/`pipeline_version`.
2. `ks-llm-cache`: ключ `sha256(prompt_id + version + model_id + canonical_json(vars))`, флаг выключения.
3. Этапы обогащения:
   - `classify_sections`;
   - чанкинг по типам (`procedure` / `qa` / `reference`);
   - `chunk_context` + проверка перекрытия слов;
   - `extract_facts` + grounding (оба режима);
   - привязка к сущностям + `disambiguate_entity`;
   - юниты `question` (+ `generate_questions` под флагом).
4. Полный `review.md` в dry-run.

**Готово, когда** (ТЗ): тесты grounding, валидации JSON, повтора при невалидном JSON и привязки на фейковом реестре зелёные.
**Зависит от:** для контура — Q8 (structured output, thinking).

2. Ветки `facts.bm25` и `facts.knn`; `EntityScope` `Off` / `Boost` / `Filter` с проверкой в JSON; fallback при `< MinResults`; `attribute_lookup`.

## Риски

- **Нет контрактов** FRIDA, вики и оргструктуры. Адаптеры источников будут конфигурируемыми по полям, но могут потребовать доработки после того, как пользователь увидит реальные маппинги в контуре. `check` и `--dry-run` нужны, чтобы это всплыло до полной индексации.
- **`TreatWarningsAsErrors`**: новые пакеты и анализаторы могут ломать сборку. Проверять сразу при добавлении.
- **Код не проверяется на инфраструктуре.** Корректность запросов к OpenSearch гарантируется только JSON-тестами. Поведение анализаторов, kNN-фильтра и structured output Gemma проверяется интеграционными тестами и `check` у пользователя.
