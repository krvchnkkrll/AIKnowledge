## 2. Контекст и цель

### 2.1. Зачем этот прототип

Проверить на golden set, какие изменения реально улучшают поиск по вики. Главная цель — **измеримость**: каждая гипотеза включается флагом конфигурации, eval-раннер сравнивает конфигурации между собой и с текущим поиском.

### 2.2. Проблемы, которые решаем

1. **Размывание чанков.** Один чанк содержит несколько независимых тем (адрес, телефон, режим работы). Статья-список «режимы работы всех организаций» выигрывает по релевантности у карточки конкретной организации, а в контекст попадает много лишнего.
2. **Разрыв между системами.** Сведения об организации «Ветерок» лежат в оргсервисе, а её телефон и адрес — в статье вики. Поиск не знает, что это одна сущность.
3. **Имена собственные теряются в векторном поиске.** Запрос «режим работы Ветерка» находит статьи про режимы работы вообще, потому что имя организации — слабый сигнал для эмбеддинга.

### 2.3. Гипотезы (каждая — флаг)

| Код | Гипотеза | Флаг |
|---|---|---|
| H1 | Гибрид BM25 + kNN лучше чистого kNN | `Retrieval.Branches` |
| H2 | Фильтр/буст по разрешённой сущности убирает чужие статьи | `Retrieval.EntityScope` = `Off` / `Boost` / `Filter` |
| H3 | Атомарные факты из справочных секций лучше чанков для вопросов «атрибут сущности» | `Retrieval.UseFacts` |
| H4 | Прямой ответ из атрибутов карточки сущности, без поиска | `Retrieval.UseAttributeLookup` |
| H5 | Контекстный префикс чанка улучшает поиск | `Ingestion.ContextualPrefix` (требует переиндексации) |
| H6 | Реранкер улучшает порядок | `Retrieval.Rerank.Enabled` |
| H7 | Меньше токенов в контексте при той же полноте | метрика `ContextTokens` |

### 2.4. Фазы

- **Фаза 1 (делать сейчас):** Вики (база знаний) + Оргструктура как справочник сущностей.
- **Фаза 2 (НЕ делать):** Электронный архив (ГОСТы, стандарты, инструкции). В коде оставить только точки расширения из раздела 13.

## 3. Ограничения среды и как с ними работать

Агент не может проверить код на реальной инфраструктуре. Поэтому:

1. **Все внешние зависимости — за интерфейсами** (порты, раздел 4.2). Реальные адаптеры пишутся строго по контрактам из репозитория.
2. **Для каждого порта — фейк** для unit-тестов: in-memory OpenSearch-хранилище не нужно, достаточно фейков на уровне портов. Фейковый эмбеддер — детерминированный (например, хэш токенов в вектор нужной размерности), чтобы тесты поиска были воспроизводимыми.
3. **Построение запросов к OpenSearch тестируется по JSON**: тест сравнивает сгенерированное тело запроса с ожидаемым (snapshot или явная проверка ключевых узлов).
4. **Интеграционные тесты** против реальной инфраструктуры — помечены отдельной категорией/трейтом и пропускаются, если не задана переменная окружения (например, `KS_INTEGRATION=1`). Их запускает пользователь в контуре.
5. **CLI-команда `check`** — первая, что запускает пользователь в контуре: пинг OpenSearch, тестовый эмбеддинг FRIDA (проверка размерности), тестовый JSON-ответ Gemma по схеме, тестовый вызов реранкера. Понятный вывод «OK / FAIL + причина».
6. **Итоговый `RUNBOOK.md`** — пошаговая инструкция для пользователя: что настроить, какие команды выполнить, где смотреть результаты.

## 5. Модель данных и индексы

### 5.1. Общие правила

- Имя индекса: `{Prefix}{name}-v{N}`, поиск и запись — через алиас `{Prefix}{name}`. Пересборка = создать `v{N+1}`, наполнить, переключить алиас. Команда CLI для этого.
- Текстовые поля — русский анализ: встроенный анализатор `russian` для основного поля плюс подполе `.exact` с `lowercase` + `asciifolding` (или без него, если ломает кириллицу — проверь тестом) для точных совпадений. Нормализация `ё → е` в char_filter.
- Векторное поле: `knn_vector`, размерность из `IEmbeddingClient.Dimensions` (для FRIDA — 1536, но брать из контракта/конфига), HNSW, пространство — cosine или innerproduct для нормализованных векторов. Движок и параметры HNSW — из конфигурации.
- Все даты — UTC, ISO 8601.

### 5.5. `ks-ingest-state` — состояние индексации

По одному документу на исходный документ: `source`, `doc_id`, `content_hash`, `doc_updated_at`, `status` (`pending` / `done` / `failed` / `deleted`), `error`, `pipeline_version`, `processed_at`, счётчики (чанков, фактов, отброшенных grounding-проверкой, непривязанных упоминаний).

### 5.6. `ks-llm-cache` — кэш ответов LLM

Ключ: `sha256(prompt_id + prompt_version + model_id + canonical_json(variables))`. Значение: сырой ответ, распарсенный JSON, время, длительность. Повторная индексация без изменений не должна вызывать LLM. Кэш выключается флагом.

## 6. Индексация

### 6.0. Эмбеддинги FRIDA — обязательные правила

- Документы эмбеддятся с префиксом `search_document: `, запросы — с `search_query: `. **Сначала выясни по контракту**, добавляет ли их сервис FRIDA сам. Если да — не добавлять повторно. Если нет — добавлять в `IEmbeddingClient`. Решение и доказательство (ссылка на код контракта) — в `REPO_NOTES.md`. Тест: префикс добавляется ровно один раз.
- Лимит входа модели — 512 токенов. Бюджет юнита (текст + контекстный префикс + заголовок) — не больше `Chunking.MaxTokens` (по умолчанию 380) + `Chunking.MaxPrefixTokens` (по умолчанию 80). Если контракт FRIDA отдаёт число токенов или признак обрезки — использовать. Если нет — консервативная оценка `символы / Chunking.CharsPerToken` (по умолчанию 3.0), значение настраивается. Любое превышение лимита логировать и считать в метриках индексации.
- Батчи и параллелизм — по ограничениям из контракта.

### 6.1. Реестр сущностей из оргструктуры (без LLM)

1. Прочитать все записи `IOrgSource.ListAllAsync`.
2. Для каждой записи построить `entity_id`, `canonical_name`, `parent_entity_id`, `summary` (из доступных полей).
3. **Детерминированная генерация алиасов** (чистая функция, покрыть тестами):
    - Организации: полное и краткое наименование, без организационно-правовой формы (ООО, АО, ПАО, ЗАО, ОАО, ИП, ФГУП, ГУП, МУП, ГБУ, ГКУ, МБУ, АНО, НКО — список в конфиге), без кавычек любого вида (`«»"'„“`), аббревиатура, если есть в данных.
    - Подразделения: полное название, название без типа («отдел», «управление», «служба», «сектор» — список в конфиге), аббревиатура, если есть.
    - Сотрудники: «Фамилия Имя Отчество», «Фамилия И. О.», «И. О. Фамилия», «Фамилия Имя», «Фамилия».
4. **Нормализация для `aliases_norm`**: нижний регистр, `ё → е`, удалить кавычки и пунктуацию, схлопнуть пробелы, trim.
5. Запись bulk-операцией, удаление сущностей, которых больше нет в источнике.

### 6.2. Вики

#### 6.2.1. Чтение и инкрементальность

- `ingest wiki --full` — все статьи; `--incremental` — `changedSince` = последняя успешная дата из состояния; `--limit N`, `--ids a,b,c` — для отладки.
- Для каждой статьи считать `content_hash` нормализованного HTML. Если хэш и `pipeline_version` не изменились — пропустить.
- **Удаления**: после полного прохода все `doc_id` из состояния, которых нет в источнике, помечаются `deleted`, их юниты и факты удаляются, ссылки из `ks-entities.linked_doc_ids` и `attributes` с этим `source_doc_id` вычищаются.
- Переиндексация документа = удалить все его юниты и факты, записать заново (не патчить).

#### 6.2.2. HTML → структура

Детерминированный парсер (библиотеку выбрать по политике репозитория; если можно добавлять пакеты — AngleSharp). Выход: `ParsedDocument { title, sections[] }`, где секция: `section_id`, `level`, `heading`, `heading_path`, `blocks[]`.

Правила (каждое — тест):

- Границы секций — `h1`–`h4`. Текст до первого заголовка — секция с заголовком статьи.
- Каждый `li` → отдельное предложение; если нет терминальной пунктуации — добавить точку.
- Таблица → markdown-таблица; строки таблицы не разрывать между чанками. Если таблица больше лимита — резать по строкам, повторяя шапку.
- Удалить скрипты, стили, навигацию, пустые элементы; ссылки → текст ссылки; изображения → `alt`, если есть.
- Нормализация пробелов и неразрывных пробелов.

#### 6.2.3. Классификация секций (LLM, один вызов на статью)

Промпт `classify_sections`: на вход — заголовок статьи и список секций (заголовок + первые `N` символов). Выход по JSON schema:

```json
{
  "primary_entity_mention": "string | null",
  "sections": [
    { "section_id": "string", "type": "reference|procedure|qa|narrative", "entity_mentions": ["string"] }
  ]
}
```

Определения типов (включить в промпт):
- `reference` — справочные сведения: контакты, адреса, режимы работы, реквизиты, списки однотипных записей.
- `procedure` — инструкция, последовательность шагов.
- `qa` — вопросы и ответы.
- `narrative` — описательный текст.

Если флаг `Ingestion.ClassifySections = false` — все секции `unknown`, обработка как `narrative`.

#### 6.2.4. Чанкинг по типу секции

| Тип | Правило |
|---|---|
| `procedure` | Секция целиком, если влезает в бюджет. Иначе — по подзаголовкам, затем по шагам; шаги не разрывать. |
| `qa` | Одна пара «вопрос — ответ» = один юнит `qa_pair`. Вопрос дополнительно индексируется как юнит `question` с `parent_unit_id` (раздел 6.2.8). |
| `reference` | Чанки по границам блоков (строки списков, строки таблиц) в пределах бюджета. **Плюс** извлечение фактов (6.2.6). |
| `narrative` / `unknown` | По абзацам в пределах бюджета, без перекрытия (перекрытие — параметр конфигурации, по умолчанию 0). |

Чанкинг — чистая функция от `ParsedDocument` + типов секций; покрыть тестами.

#### 6.2.5. Контекстный префикс (H5, флаг `Ingestion.ContextualPrefix`)

Промпт `chunk_context`: на вход — заголовок статьи, оглавление (heading paths), текст секции, текст чанка. Выход: 1–2 предложения, до `MaxPrefixTokens`, которые **добавляют** контекст: чья это информация, о чём раздел, к какому объекту относится. Запрещено пересказывать сам чанк.

Проверка качества (детерминированная): если префикс на >70% (коэффициент в конфиге) состоит из слов самого чанка — считать бесполезным, не использовать, увеличить счётчик. Для экономии вызовов допускается батч: все чанки одной секции в одном вызове.

#### 6.2.6. Факты из справочных секций (H3, флаг `Ingestion.ExtractFacts`)

Только для секций `reference`. Промпт `extract_facts`. Выход:

```json
{
  "facts": [
    {
      "text": "Режим работы организации «Ветерок»: с 8:00 до 20:00 по будням.",
      "entity_mention": "Ветерок",
      "entity_type": "organization|department|person|null",
      "attribute": "address|phone|email|working_hours|reception_hours|website|other_contact|null",
      "value": "с 8:00 до 20:00 по будням",
      "evidence": "Режим работы: с 8 до 20 (пн–пт)"
    }
  ]
}
```

Требования к промпту:
- Каждый факт самодостаточен: субъект назван явно, местоимения заменены, **все условия сохранены** («по будням», «кроме пятницы», «летом», «для физлиц»).
- `evidence` — дословная цитата из текста секции.
- Одна запись в списке/строка таблицы про другую организацию = отдельный факт со своей сущностью.
- Если атрибут не из закрытого списка — `attribute: null`, факт всё равно сохраняется.
- Закрытый список атрибутов — в конфигурации, подставляется в промпт и в JSON schema.

**Grounding-проверка** (чистая функция, тесты обязательны):
- `evidence` после нормализации (регистр, пробелы, `ё → е`, типы тире и кавычек) — подстрока нормализованного текста секции. Иначе факт отбрасывается.
- Если `attribute != null`: ключевые токены `value` (цифры, время, телефонные цифры, email) присутствуют в `evidence`. Иначе атрибут обнуляется (факт остаётся без атрибута) или факт отбрасывается — режим в конфиге, по умолчанию «обнулить атрибут».
- Счётчики: извлечено / отброшено / атрибут обнулён.

#### 6.2.7. Привязка к сущностям

Для каждого упоминания (`primary_entity_mention`, `entity_mentions` секций, `entity_mention` фактов):

1. Нормализовать (как алиасы) и искать в `ks-entities`: точное совпадение по `aliases_norm`, затем match по `aliases` (russian) с fuzziness из конфига. Фильтр по `type`, если он известен.
2. Ровно один кандидат с точным совпадением → привязка.
3. Несколько кандидатов → промпт `disambiguate_entity`: упоминание, предложение-контекст, заголовок статьи, до 5 кандидатов (имя, тип, родитель, summary). Ответ: `entity_id` или `null`.
4. Ни одного кандидата или `null` → в `unlinked_mentions`.

Результат:
- Факт получает `entity_ids` своей сущности.
- Чанк получает `entity_ids` сущностей, **упомянутых в его тексте** (не всей статьи и не всей секции). Проверка упоминания в тексте чанка — по алиасам сущности.
- Сущность получает `doc_id` в `linked_doc_ids`, а факты с `attribute` — в `attributes`.

#### 6.2.8. Вопросы-указатели (флаг `Ingestion.QuestionUnits`)

- Для `qa_pair` вопрос индексируется отдельным юнитом `question`.
- Опционально (флаг `Ingestion.GenerateQuestions`, по умолчанию выключен) — промпт `generate_questions`: 2–4 вопроса к чанку `procedure`/`narrative`, которые пользователь мог бы задать. Каждый — юнит `question` с `parent_unit_id`.
- При поиске попадание в `question` засчитывается его родителю.

#### 6.2.9. Надёжность

- Ошибка одного документа не останавливает пайплайн: статус `failed` + текст ошибки, идём дальше.
- LLM: `temperature = 0`, режим размышлений выключен для извлечения (настраивается), ответ валидируется по схеме; при невалидном JSON — один повтор с текстом ошибки в промпте, потом отказ.
- Ограничение параллелизма LLM и эмбеддингов — из конфигурации.
- Сводка в конце прогона: документы (обработано / пропущено / ошибки), юниты, факты, grounding, привязка (привязано / неоднозначно / не найдено), превышения лимита токенов, вызовы LLM (из кэша / новые), время.

#### 6.2.10. Режимы отладки (обязательно)

- `ingest wiki --dry-run --sample N` — обработать N статей, **ничего не писать** в OpenSearch, сохранить в `out/ingest-dryrun-<timestamp>/`: разобранную структуру, типы секций, чанки с префиксами, факты с результатом grounding, результаты привязки. Формат — JSONL + человекочитаемый `review.md`.
- `inspect doc <doc_id>` — показать, что лежит в индексах по документу.
- `inspect entity <name|id>` — карточка сущности, атрибуты, связанные документы.

Это главный инструмент пользователя для оценки качества извлечения до полной индексации.

## 7. Поиск

### 7.1. Поток

```
query → [1] кандидаты сущностей → [2] QueryPlan (LLM) → [3] ветки поиска
      → [4] слияние (RRF) → [5] реранк → [6] сборка контекста → ответ + trace
```

### 7.2. Кандидаты сущностей (без LLM)

Весь текст запроса — match-запрос по `aliases` и точное совпадение нормализованных n-грамм запроса (1–4 слова) с `aliases_norm`. Top-K кандидатов (`Planning.EntityCandidates`, по умолчанию 5) с score.

### 7.3. QueryPlan (LLM, флаг `Planning.UseLlm`)

Промпт `plan_query`: запрос пользователя, кандидаты сущностей, закрытый список атрибутов. Выход:

```json
{
  "intent": "attribute_lookup|entity_info|howto|factual|general",
  "entity_ids": ["org:123"],
  "attribute": "working_hours|null",
  "semantic_query": "режим работы",
  "needs_clarification": false,
  "clarification_question": null
}
```

- `entity_ids` — только из переданных кандидатов (валидировать; лишние отбрасывать).
- `semantic_query` — запрос без имени сущности, если сущность выбрана.
- Если `Planning.UseLlm = false` — детерминированный план: сущность = top-1 кандидат с точным совпадением алиаса, `semantic_query` = исходный запрос, `intent = general`.

### 7.4. Ветки поиска

| Ветка | Индекс | Запрос |
|---|---|---|
| `chunks.bm25` | ks-chunks | multi_match по `text`, `context_prefix`, `heading_path`, `doc_title` (веса в конфиге) |
| `chunks.knn` | ks-chunks | kNN по эмбеддингу `semantic_query` |
| `facts.bm25` | ks-facts | match по `text` |
| `facts.knn` | ks-facts | kNN |
| `attributes` | ks-entities | прямое чтение `attributes` сущности (H4) |

- Состав веток — `Retrieval.Branches`.
- `EntityScope`: `Off` — без учёта сущности; `Boost` — `should` по `entity_ids` с весом из конфига; `Filter` — `filter` по `entity_ids` (для kNN — pre-filter / efficient filter, как поддерживает версия OpenSearch; иначе post-filter с увеличенным `k`, записать в `REPO_NOTES.md`).
- В `Filter`-режиме, если результатов меньше `MinResults`, выполнить повтор без фильтра и отметить в trace (fallback).
- Размер выборки каждой ветки — `Retrieval.BranchTopK` (по умолчанию 50).
- Фильтр по `access` применяется во всех ветках, если включён (раздел 11).

### 7.5. `attribute_lookup` (H4, флаг `Retrieval.UseAttributeLookup`)

Если `intent = attribute_lookup`, есть `entity_ids` и `attribute`, а у сущности есть этот атрибут — вернуть значения атрибута с `evidence` и источником как результат с наивысшим приоритетом. Остальные ветки всё равно выполняются (для оценки), но в контекст идут после атрибутов.

### 7.6. Слияние

- Юниты `question` заменяются на родителя (score родителя = max).
- RRF в C#: `score = Σ w_branch / (k + rank)`, `k` и веса — в конфиге (по умолчанию `k = 60`, веса 1.0). Ранги считаются с 1. Ничьи — детерминированно по `unit_id`.
- Дедупликация: один `unit_id` — один результат. Опционально (`Retrieval.MaxUnitsPerDoc`) — не больше N юнитов на документ.
- Чистая функция, тесты обязательны.

### 7.7. Реранк (H6)

Top `Rerank.Candidates` (по умолчанию 30) после слияния → `IReranker`. Текст для реранка — `heading_path + text` (факты — `text`). Адаптер по умолчанию — HTTP в формате Hugging Face TEI `/rerank` (`{"query": "...", "texts": [...]}` → `[{"index": i, "score": s}]`); формат и URL — в конфиге. При ошибке реранкера — вернуть порядок после слияния, отметить в trace.

### 7.8. Сборка контекста

Порядок блоков:
1. Карточка сущности: имя, тип, `summary`; если есть `IOrgSource.GetUnitAsync` — живые данные (руководитель, родитель, дочерние) с пометкой «источник: оргсервис».
2. Атрибуты (для `attribute_lookup`).
3. Факты.
4. Чанки. Для `intent = howto` чанк раскрывается до полной секции (`section_id`), если влезает в бюджет (`Context.ExpandToSectionForIntents`).

Требования:
- Бюджет — `Context.MaxTokens` (по умолчанию 2000), оценка токенов — как в 6.0. Что не влезло — отрезается и отмечается в trace.
- У каждого блока метка источника: `[wiki | {doc_title} | {heading_path} | {doc_updated_at:yyyy-MM-dd} | {doc_url}]`.
- Факты и строки справочных чанков, привязанные к сущностям, получают префикс с именем сущности: `[Ветерок] ...`.
- Выход — и готовый текст, и структурированный список блоков.

### 7.9. Trace (обязательно)

Каждый поиск возвращает (при `debug = true`) и сохраняет для eval:
- план (сырой ответ LLM + провалидированный);
- кандидаты сущностей со score;
- по каждой ветке: список `unit_id`, `doc_id`, rank, score;
- после слияния, после реранка, в финальном контексте — то же;
- срабатывание fallback'ов;
- тайминги каждой стадии;
- число токенов контекста.

## 9. Eval-раннер (главный результат прототипа)

### 9.1. Golden set

- Найти golden set в репозитории (путь из раздела 0 или поиск). Описать формат в `REPO_NOTES.md`.
- Внутренняя модель:

```csharp
record GoldenItem(
    string Id,
    string Question,
    string? Category,
    IReadOnlyList<string> ExpectedDocIds,           // статьи вики
    IReadOnlyList<string> ExpectedEntityIds,        // если есть
    IReadOnlyList<string> ExpectedAnswerSubstrings  // если есть
);
```

- Написать адаптер из фактического формата. Если ожидаемые документы заданы не id, а URL или заголовками — сопоставить через индекс, несопоставленные записи вывести в отчёт отдельным списком.
- Метрики, для которых нет данных в golden set, пропускаются (не ломают прогон).
- Если категорий нет — ввести эвристические (`attribute`, `howto`, `other`) через простой классификатор по ключевым словам, в отчёте пометить, что категории эвристические.

### 9.2. Конфигурации прогонов

Файл `eval/configs.json` (путь — как удобно в репо): список именованных конфигураций как переопределений флагов. Предзаполнить:

| Имя | Суть |
|---|---|
| `dense` | только `chunks.knn`, без сущностей, без реранка |
| `hybrid` | `chunks.bm25` + `chunks.knn` |
| `hybrid_entity_boost` | + `EntityScope = Boost` |
| `hybrid_entity_filter` | + `EntityScope = Filter` |
| `facts` | + ветки фактов |
| `facts_attr` | + `UseAttributeLookup` |
| `full_rerank` | всё + реранк |
| `legacy` | текущий поиск чата (см. 9.3) |

Конфигурации, требующие другой индексации (H5), сравниваются через разные версии индекса: параметр `indexAlias` в конфигурации прогона.

### 9.3. Сравнение с текущим поиском

Если в репозитории есть код текущего поиска по индексу вики — адаптер `LegacySearchAdapter`, который вызывает его и приводит результат к тому же формату (`doc_id` + rank). Это базовая линия. Если код текущего поиска не удаётся переиспользовать без его рефакторинга — не рефакторить, записать в `OPEN_QUESTIONS.md`.

### 9.4. Метрики

По каждой конфигурации, в целом и по категориям:

| Метрика | Определение |
|---|---|
| `Hit@1/3/5/10` | хотя бы один ожидаемый документ в top-K результатов (уровень документа) |
| `MRR@10` | по первому ожидаемому документу |
| `nDCG@10` | бинарная релевантность по документам |
| `CandidateRecall` | ожидаемый документ есть среди кандидатов до реранка |
| `ContextHit` | ожидаемый документ попал в собранный контекст |
| `AnswerInContext` | хотя бы одна `ExpectedAnswerSubstring` (нормализованно) есть в тексте контекста |
| `ContextTokens` | среднее и p95 |
| `EntityAccuracy` | выбранные планом `entity_ids` совпали с ожидаемыми |
| `Latency` | p50/p95 по стадиям |

### 9.5. Анализ потерь (обязательно)

Для каждого вопроса, где ожидаемый документ не попал в контекст, определить первую стадию потери:
`not_indexed` → `not_in_any_branch` → `lost_in_fusion` → `lost_in_rerank` → `cut_by_budget` → `wrong_entity_filter`.
Сводка по причинам — в отчёт.

### 9.6. Выход

`out/eval-<timestamp>/`:
- `summary.md` — таблица конфигураций × метрик, по категориям, анализ потерь, топ-20 вопросов, где конфигурации расходятся сильнее всего;
- `per-question.jsonl` — для каждой пары (вопрос, конфигурация): ранги ожидаемых документов, причина потери, токены, trace;
- `configs.json` — точные параметры прогона и версии индексов/промптов.

CLI: `eval --golden <path> --configs <path> [--only name1,name2] [--limit N]`.

Опционально (флаг `--generate-answers`): сгенерировать ответ Gemma по контексту лучшей конфигурации и сохранить рядом для ручного просмотра. Автоматическую оценку ответов не делать.

## 12. Этапы и критерии готовности

Порядок выбран так, чтобы как можно раньше получить **первый прогон golden set** (базовую линию), а затем добавлять гипотезы.

### Этап 0. Изучение репозитория
- Заполнить `REPO_NOTES.md`: целевой фреймворк, структура решения, DI/Options/логирование, стиль, тестовый фреймворк, контракт FRIDA (префиксы, размерность, батчи, лимиты, наличие счётчика токенов), подключение Gemma (клиент, structured output, режим размышлений), клиент OpenSearch и версия (если видна), маппинги индексов вики и оргструктуры, модель статьи вики (где HTML, где дата изменения, есть ли права), доступ к оргданным, код текущего поиска, golden set (путь, формат, объём, категории).
- Заполнить `OPEN_QUESTIONS.md`.
- **Готово, когда:** оба файла есть, план этапов уточнён в `PROGRESS.md`. Код не пишется.

### Этап 1. Каркас
- Проекты, DI, конфигурация, порты, фейки, реальные адаптеры FRIDA/Gemma/OpenSearch/реранкера по контрактам, управление индексами (создание версий, алиасы), CLI `check`.
- **Готово, когда:** решение собирается, unit-тесты на фейках зелёные, `check` реализован, маппинги индексов покрыты тестами (JSON).

### Этап 2. Реестр сущностей
- 6.1 целиком, CLI `ingest orgs`, `inspect entity`.
- **Готово, когда:** тесты генерации и нормализации алиасов (включая сотрудников и ОПФ) зелёные.

### Этап 3. Базовая индексация вики (без LLM)
- 6.2.1, 6.2.2, 6.2.4 (все секции как `unknown`), 6.0, запись в `ks-chunks`, состояние, удаления, `--dry-run --sample`.
- **Готово, когда:** тесты парсера HTML, чанкинга и бюджета токенов зелёные; повторный прогон без изменений ничего не переиндексирует (тест на фейках).

### Этап 4. Базовый поиск и eval → первая базовая линия
- Ветки `chunks.bm25` и `chunks.knn`, RRF, сборка контекста, trace, `/api/search`, `/api/context`, CLI `search`.
- Eval-раннер целиком (раздел 9) для конфигураций `dense`, `hybrid`, `legacy`.
- **Готово, когда:** тесты RRF, сборки контекста и метрик (на синтетических данных с известным ответом) зелёные; `RUNBOOK.md` содержит шаги до первого прогона eval.

### Этап 5. LLM-обогащение
- 6.2.3, 6.2.5, 6.2.6, 6.2.7, 6.2.8, кэш LLM, промпты в ресурсах, `review.md` в dry-run.
- **Готово, когда:** тесты grounding-проверки, валидации JSON-ответов, повтора при невалидном JSON, привязки сущностей (на фейковом реестре) зелёные.

### Этап 6. Поиск с учётом сущностей и фактов
- 7.2, 7.3, ветки фактов, `EntityScope`, 7.5, fallback, 7.7, раскрытие до секции, анализ потерь.
- Все конфигурации eval из 9.2.
- **Готово, когда:** тесты плана (валидация `entity_ids` против кандидатов), фильтра/буста в JSON-запросе, fallback, реранка с ошибкой зелёные.

### Этап 7. Runbook
- `RUNBOOK.md`: конфигурация, `check`, `ingest orgs`, `ingest wiki --dry-run --sample 20` и что смотреть в `review.md`, полная индексация, `eval`, как читать `summary.md`, как пересобрать индекс с другим флагом (H5), типичные ошибки.
- **Готово, когда:** пользователь может пройти путь от пустого кластера до отчёта eval только по этому файлу.

### Этап 8 (опционально, только по явной просьбе). Интеграция
- MCP-сервер поверх тех же сервисов (официальный C# SDK MCP, хостинг в ASP.NET Core): инструменты `search`, `get_entity`, `get_context`.
- Context provider для чата на Agent Framework, вызывающий `/api/context`.

## 13. Фаза 2 (архив) — только точки расширения, не реализовывать

Чтобы потом не переделывать:
- `source` в `ks-chunks` уже есть; маппинг допускает поле `doc_code` (object: `type`, `num`, `year`, `canonical`) — добавить в маппинг сразу, не заполнять.
- В `QueryPlan` предусмотреть пустой список `identifiers`; интерфейс `IIdentifierParser` с реализацией-заглушкой, возвращающей пустой результат.
- Ветки поиска регистрируются через общий интерфейс, чтобы добавить `archive.*` без изменения слияния.
- В сборке контекста — поддержка источника `archive` в метке блока.
